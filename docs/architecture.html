Architecture Overview

Factory Inventory Management System

A full-stack demo application for inventory, order, demand, and spending analytics — Vue 3 single-page frontend backed by a FastAPI service that reads from static JSON files held in memory. No database, no persistence between restarts.

Vue 3 · Composition API FastAPI · Pydantic In-memory JSON data No auth · demo only

Tech Stack

Two independently-run dev servers, connected only over HTTP.

Frontend

  • Vue 3 (Composition API)
  • Vue Router (client-side routing)
  • Vite (dev server / bundler)
  • Axios (HTTP client, in api.js)
vite dev — localhost:3000

Backend

  • Python + FastAPI
  • Pydantic (request/response models)
  • Uvicorn (ASGI server)
  • CORS open to all origins (dev only)
uvicorn — localhost:8001 · /docs

Data

  • Static JSON files in server/data/
  • Loaded once at startup by mock_data.py
  • Held in memory, filtered per-request
  • No database — restart discards any writes
7 JSON files, ~9K lines total

Request/response path from a user action to rendered data.

Data Flow: applying a filter

The dashboard's four filters (Time Period, Warehouse, Category, Order Status) all follow this same path.

1

User changes a control in FilterBar.vue, updating shared state in the useFilters composable.

2

A view (e.g. Dashboard.vue) reacts and calls a method on api.js, passing the current filter values.

3

api.js builds query params and skips any filter set to 'all', then makes an axios GET request.

4

FastAPI's route handler runs apply_filters() / filter_by_month() over the in-memory Python lists.

5

The filtered result is validated against a Pydantic response model and serialized to JSON.

6

The view stores the response in a ref (e.g. allOrders); computed properties derive totals, charts, and tables from it.

Key Subsystems

Filter system

Four filters (Time Period, Warehouse, Category, Order Status) are shared via useFilters and passed as query params to nearly every endpoint. Inventory has no time dimension, so month/quarter filtering only applies to orders and the dashboard summary.

i18n

useI18n switches between en/ja string tables in locales/, persists the choice in localStorage, and drives currency formatting (USD ↔ JPY) via utils/currency.js.

Auth (mocked)

useAuth returns a hardcoded current user with no real session or backend check — it exists purely to populate the profile menu and vary display name/locale.

Reports

/api/reports/quarterly and /api/reports/monthly-trends aren't stored data — they're aggregated on every request by looping over the full orders list.

Notes for anyone extending this

  • The frontend's api.js defines getTasks, createTask, deleteTask, toggleTask, createPurchaseOrder, and getPurchaseOrderByBacklogItem — but no matching routes exist in server/main.py. Task calls fail silently (caught and logged) and the UI falls back to mock tasks embedded in useAuth.
  • A CreatePurchaseOrderRequest Pydantic model is defined server-side but has no route wired to it — purchase orders are currently read-only, loaded straight from purchase_orders.json.
  • All data resets on backend restart. Anything that looks like a "write" (tasks, purchase orders) either doesn't persist or doesn't actually reach the server.
